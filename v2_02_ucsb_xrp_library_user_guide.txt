USING THE UCSB-XRP LIBRARY
User guide


PURPOSE

UCSB-XRP provides the common structure used by the course robot programs. It
connects motion commands to the XRP motors, converts encoder readings to
physical units, estimates pose, follows world-coordinate destinations, creates
an occupancy grid from a dimensioned map, and plans a route through free cells.

XRPBot is the only UCSB-XRP class that calls XRPLib directly. Most programs use
Robot and the higher-level controllers rather than accessing XRPBot.


THE LIBRARY IN ONE PAGE

Lower-level motion

MotionCommand
    requested forward speed and turn rate

DifferentialDrive
    converts the MotionCommand to WheelSpeeds

WheelSpeedController
    converts target and measured WheelSpeeds to DriveCommand

XRPBot
    sends DriveCommand to the hardware

Measurement and pose

XRPBot
    returns RawSensors

SensorModel
    converts encoder, time, range, and USER-button readings to wheel position,
    wheel-travel increments, regularized wheel speed, elapsed time, range, and
    button state in Measurements

Odometry
    converts measured left and right wheel travel to Pose

Navigation and planning

NavigationController
    converts Pose and the current NavigationGoal to a MotionCommand

ArenaMap
    stores the supplied dimensioned arena description

OccupancyGrid
    samples ArenaMap at a chosen resolution

GridPlanner
    converts start and destination GridCell values to a GridPath

DeliveryMission
    combines stationary range observation, map selection, planning, and
    navigation for the final course task


UNITS AND DIRECTIONS

- Distance, position, wheel travel, map coordinates, and grid resolution use
  millimeters.
- Linear and wheel speed use millimeters per second.
- Hardware timestamps use integer milliseconds.
- Heading and heading change use radians.
- Turn rate uses radians per second.
- Each left/right drive command is a normalized dimensionless value from -1
  to +1 before the configured limit and motor signs are applied.

World positive x normally points in the robot's initial forward direction.
World positive y points to its left. Heading zero is world positive x, and
positive heading is counterclockwise. Positive speed for either wheel means
forward wheel motion.

RobotConfig contains the motor and encoder signs that make these conventions
independent of the physical wiring.


PROJECT FILES

main.py
    Imports the current task, constructs objects, and runs the standard loop.

robot_config.py
    Contains RobotConfig and NavigationConfig values measured or selected for
    one robot.

sensor_model.py, wheel_speed_controller.py, differential_drive.py,
odometry.py, navigation_controller.py, grid_planner.py
    Each file defines the class named by the file. Early challenges include
    only the classes introduced so far.

course_setup.py
    Selects the supplied class or the class in the named project file for each
    component and provides the make_* factory functions.

challenge.py
    Loads world-owned task values and defines any non-geometric task settings,
    such as a target time, grid resolution, or range threshold.

world.json
    Defines the project worlds used by Python, the simulator, and the Monitor:
    bounds, initial pose, obstacles, changeable features, and named markers.

Task values belong in challenge.py. Robot measurements and reusable controller
settings belong in robot_config.py. World geometry belongs in world.json and is
loaded rather than copied into Python. Each algorithm belongs in its literally
named component file. Use # for ordinary comments. Triple-quoted strings at
the start of a module, class, or function are documentation strings, not a
general commenting syntax.


LOADING THE PROJECT WORLD

load_world() reads world.json and returns the selected ProjectWorld. With no
arguments, it loads the catalog's default_world:

    from ucsb_xrp import load_world


    WORLD = load_world()
    INITIAL_POSE = WORLD.initial_pose
    ROUTE = WORLD.waypoints()

waypoint(name) returns one named NavigationGoal. waypoints() returns all
waypoint markers in file order. arena_map(blocked_features=()) returns the
dimensioned ArenaMap for planning. The project therefore has one source for
geometry; the Python task, virtual XRP, and Monitor do not maintain separate
coordinates.


SELECTING THE SUPPLIED OR PROJECT-FILE CLASS

Each of the six components has a supplied class and a class in
the corresponding project file. Both classes have the same public methods.
Code obtains the selected class from course_setup.py, so the rest of the
program is unchanged when a selection changes.

course_setup.py contains one explicit Boolean per component:

    USE_STUDENT_SENSOR_MODEL = False
    USE_STUDENT_WHEEL_SPEED_CONTROLLER = False
    USE_STUDENT_DIFFERENTIAL_DRIVE = False
    USE_STUDENT_ODOMETRY = False
    USE_STUDENT_NAVIGATION_CONTROLLER = False
    USE_STUDENT_GRID_PLANNER = False

False selects the supplied class and True selects the class in the named
project file. The file initially selects all supplied classes;
change one named flag at a time after the corresponding class passes its
software tests. Early challenge projects contain only the flags for components
introduced so far.


PHYSICAL XRP SETUP AND PROJECT RUNS

Use the browser's XRP setup/repair page over USB-C to install or repair the
persistent course runtime and to configure the robot's Wi-Fi profile. This
runtime includes MicroPython, XRPLib, the UCSB-XRP library, supplied component
classes, and the robot service.

After setup, an IDE Run uses the selected local Wi-Fi connection. It checks the
project structure, compiles every Python file, sends the project to the XRP,
and starts its main Python file. Stop, program output, and telemetry use the
same Wi-Fi connection. Reset stops the program and clears its telemetry and
live values. Normal Run does not install or repair the course runtime.


RUNNING A DIRECT MOTOR EXPERIMENT

XRPBot is used directly for fixed-command motor measurements. This short
program applies the DriveCommand value supplied by challenge.py, waits for the
specified interval, and prints the encoder samples before and after the run.

motor_experiment.py

    from time import sleep_ms

    from challenge import EXPERIMENT_COMMAND, RUN_TIME_MS
    from robot_config import ROBOT_CONFIG
    from ucsb_xrp import XRPBot


    def run_motor_experiment():
        bot = XRPBot(ROBOT_CONFIG)
        bot.wait_for_button()
        bot.reset_encoders()
        start = bot.read()

        try:
            bot.set_drive(EXPERIMENT_COMMAND)
            sleep_ms(RUN_TIME_MS)
            finish = bot.read()
        finally:
            bot.stop()

        print(start)
        print(finish)


    run_motor_experiment()

EXPERIMENT_COMMAND is a DriveCommand value. The same program can be used with
the wheels raised or with the robot on the floor. This is deliberately one
open-loop timed pulse, not a sampled controller. Motor characterization may
therefore use sleep_ms; all sampled challenge control uses Robot's clock.


STARTING AND STOPPING ROBOT

make_robot() constructs Robot with the selected SensorModel,
WheelSpeedController, DifferentialDrive, and Odometry classes.

Robot.start(initial_pose) resets the encoders and component state and returns
the first RobotState. An IDE-managed Run begins immediately because selecting
Run is the start action. A program launched directly on the XRP waits for a
USER-button press and release before resetting.

Robot.step(command) runs one sample period and returns the next RobotState.
Robot maintains absolute, wrap-safe sample deadlines internally. A loop that
calls Robot.step() does not call sleep_ms(). If calculation overruns
one deadline, Robot records the overrun and advances to the next future sample
rather than accumulating drift or issuing catch-up samples.

Robot.stop() sends a zero drive command.

A program that can command motion places Robot.stop() in a finally clause.


READING ROBOTSTATE

RobotState has two fields:

state.measurements
    The newest physical measurements.

state.pose
    The newest odometry estimate.

Measurements provides:

time_ms
    Hardware timestamp.

dt_s
    Elapsed time since the preceding sensor update.

left_position_mm, right_position_mm
    Wheel travel relative to the latest SensorModel reset.

left_increment_mm, right_increment_mm
    Wheel travel during the latest sample.

left_speed_mm_s, right_speed_mm_s
    Regularized wheel-speed estimates derived from recent encoder position
    changes and sample times. The response time comes from
    RobotConfig.wheel_speed_filter_time_constant_ms.

wheel_speeds
    A WheelSpeeds value containing the two measured wheel speeds.

range_mm
    The range acquired during the current sample, or None.

button_pressed
    Current USER-button state.

Pose provides x_mm, y_mm, and heading_rad.


RUNNING A MEASURED STRAIGHT DISTANCE

StraightLineController is supplied. It uses measured wheel positions to reduce
speed near the requested distance and stop the robot.

main.py

    from challenge import INITIAL_POSE, TRAVEL_DISTANCE_MM
    from course_setup import make_robot
    from robot_config import ROBOT_CONFIG, STRAIGHT_CONFIG
    from ucsb_xrp import StraightLineController


    def run_straight_distance():
        robot = make_robot(ROBOT_CONFIG)
        straight = StraightLineController(STRAIGHT_CONFIG)

        try:
            state = robot.start(INITIAL_POSE)
            straight.start(
                measurements=state.measurements,
                distance_mm=TRAVEL_DISTANCE_MM,
            )
            while not straight.is_complete():
                command = straight.update(state.measurements)
                state = robot.step(command)
            return state
        finally:
            robot.stop()


    final_state = run_straight_distance()

TRAVEL_DISTANCE_MM comes from challenge.py. Cruise speed, approach speed,
slowdown distance, and position tolerance come from STRAIGHT_CONFIG.


FOLLOWING WORLD-COORDINATE DESTINATIONS

NavigationController accepts an ordered sequence of NavigationGoal values. Each
goal contains x and y coordinates and may contain a requested final heading.

main.py

    from challenge import INITIAL_POSE, ROUTE
    from course_setup import make_navigation_controller, make_robot
    from robot_config import NAVIGATION_CONFIG, ROBOT_CONFIG


    def run_route():
        robot = make_robot(ROBOT_CONFIG)
        navigation = make_navigation_controller(NAVIGATION_CONFIG)
        navigation.start(ROUTE)

        try:
            state = robot.start(INITIAL_POSE)

            while not navigation.is_complete():
                command = navigation.update(state.pose)
                state = robot.step(command)
            return state
        finally:
            robot.stop()


    final_state = run_route()

NavigationController.current_goal() returns the active goal.
NavigationController.update(pose) returns the next MotionCommand.
NavigationController.is_complete() reports completion of the final goal and any
requested final heading.


CREATING AN OCCUPANCY GRID

ArenaMap is a dimensioned description expressed in millimeters. OccupancyGrid
samples the map. resolution_mm specifies the side length of one grid cell.
clearance_mm specifies how far a free cell center must be from an obstacle.

planning_check.py

    from challenge import (
        ARENA_MAP,
        CLEARANCE_MM,
        DESTINATION,
        GRID_RESOLUTION_MM,
        INITIAL_POSE,
    )
    from course_setup import make_grid_planner
    from ucsb_xrp import OccupancyGrid


    grid = OccupancyGrid.from_arena(
        arena=ARENA_MAP,
        resolution_mm=GRID_RESOLUTION_MM,
        clearance_mm=CLEARANCE_MM,
    )

    start = grid.world_to_cell(
        INITIAL_POSE.x_mm,
        INITIAL_POSE.y_mm,
    )
    goal = grid.world_to_cell(
        DESTINATION.x_mm,
        DESTINATION.y_mm,
    )

    planner = make_grid_planner()
    path = planner.plan(grid, start, goal)
    print(path)

world_to_cell(x_mm, y_mm) returns the cell containing a world position or None
when the position is outside the grid.

cell_center(cell) returns the world coordinates at the center of a cell.

is_blocked(cell) reports whether a cell is unavailable.

neighbors(cell) returns the free cells that share a horizontal or vertical
edge with cell.


CONVERTING A GRID PATH TO NAVIGATION GOALS

GridPlanner.plan() returns GridPath or None. A GridPath begins with the start
cell and ends with the destination cell. Every cell is free, and each step
moves horizontally or vertically to a cell that shares an edge. The path does
not need to use the fewest cells.

GridPath.to_goals(grid, final_heading_rad) converts the path to
world-coordinate NavigationGoal values. It retains the destination and the
cells at which the path changes direction. Cells in the middle of a straight
segment do not create additional navigation goals.

The resulting goals are passed directly to NavigationController.start().


RUNNING THE DELIVERY MISSION

challenge.py supplies a DeliveryTask named DELIVERY_TASK. It contains the
initial pose, dimensioned map, grid settings, destination, named map feature,
and range-decision settings.

DeliveryMission uses the SensorModel selected inside Robot, the selected
GridPlanner, and the selected NavigationController. Its run() method performs
the stationary observation, map selection, planning, and navigation sequence.

main.py

    from challenge import DELIVERY_TASK
    from course_setup import (
        make_grid_planner,
        make_navigation_controller,
        make_robot,
    )
    from robot_config import NAVIGATION_CONFIG, ROBOT_CONFIG
    from ucsb_xrp import DeliveryMission


    def run_delivery():
        mission = DeliveryMission(
            task=DELIVERY_TASK,
            navigation=make_navigation_controller(NAVIGATION_CONFIG),
            planner=make_grid_planner(),
        )
        final_state = mission.run(make_robot(ROBOT_CONFIG))
        print(mission.result, final_state.pose)
        return final_state


    run_delivery()

DeliveryMission.result is "delivered" after successful navigation or "no_path"
when the selected map has no route to the destination.


REQUESTING RANGE OUTSIDE DELIVERYMISSION

Robot.step(command, read_range=True) requests a forward range reading at the end
of that sample period. The robot may remain stationary by passing STOP_COMMAND.

When range is not requested, Measurements.range_mm is None. It is also None
when no usable reading is returned.

Collect Measurements.range_mm from the requested samples, then call
robot.estimate_range(samples, minimum_usable). Robot delegates the calculation
to its selected SensorModel class. The method accepts a sequence
containing numeric ranges and None values and returns one range estimate, or
None when too few usable samples are present.


ADJUSTING A RUN AND WATCHING INTERMEDIATE VALUES

Use the live module for parameters that are useful to tune during an
experiment and for intermediate values that should be visible without
periodic print statements.

    from ucsb_xrp import live


    CRUISE_SPEED = live.number(
        "cruise_speed_mm_s",
        120.0,
        minimum=60.0,
        maximum=220.0,
        step=10.0,
        unit="mm/s",
        label="Cruise speed",
    )
    CONTROLLER_ENABLED = live.toggle(
        "controller_enabled",
        True,
        label="Controller enabled",
    )
    TURN_DIRECTION = live.choice(
        "turn_direction",
        "left",
        options=("left", "right"),
        label="Turn direction",
    )

The Monitor renders a compact slider, checkbox, or radio choices from these
declarations. Read the current value through CRUISE_SPEED.value,
CONTROLLER_ENABLED.value, or TURN_DIRECTION.value. Robot.start() and
Robot.step() apply all pending changes together after each call. Programs that
do not use Robot may call live.apply_updates() at the point in their loop where
new settings should take effect. A numeric range does not need to be an exact
multiple of step; the applied value is represented by the nearest available
slider step within the declared bounds.

Publish a named value when it changes or once per Robot.step() call:

    live.watch(
        "wheel_speed_error_mm_s",
        target_speed_mm_s - measured_speed_mm_s,
        unit="mm/s",
        label="Wheel-speed error",
    )

Robot publishes the values after its next update, and they appear under Live
telemetry. A watch is appropriate for current state, an error term, a selected
mode, or another compact diagnostic.

Use live.plot() when a calculated numerical value should be available as an
optional strip plot:

    live.plot(
        "wheel_speed_error_mm_s",
        target_speed_mm_s - measured_speed_mm_s,
        unit="mm/s",
        label="Wheel-speed error",
    )

The first value for a new name adds an unchecked green choice under Plot
signals. Use ordinary print statements for infrequent messages and exceptions;
use telemetry recording for complete time histories. Live values are transient
run data and do not replace robot_config.py or challenge.py as the source of
saved experiment settings.


CONFIGURATION

RobotConfig contains:

- sample period;
- wheel diameter;
- encoder counts per wheel revolution;
- effective track width;
- motor and encoder direction signs;
- left and right starting drive command;
- left and right speed-to-command calibration;
- wheel-speed estimator response time;
- wheel-speed feedback gain; and
- maximum drive command.

NavigationConfig contains:

- cruise speed;
- approach speed;
- slowdown distance;
- turn rate;
- position tolerance;
- heading tolerance; and
- the heading error at which forward travel returns to turning.

The selected classes read these named fields. Numerical values are not repeated
inside their methods.


TESTING A CLASS YOU IMPLEMENT

Each class can be tested without running a complete mission:

- SensorModel uses recorded RawSensors sequences and range samples.
- WheelSpeedController uses target and measured WheelSpeeds.
- DifferentialDrive uses MotionCommand values.
- Odometry uses a starting Pose and left and right wheel increments.
- NavigationController uses NavigationGoal and Pose sequences.
- GridPlanner uses small OccupancyGrid instances.

The API reference gives the exact construction and method signatures. Select
Test components before setting the corresponding USE_STUDENT_* flag to True.
Program output states the concrete input example before each result: PASS means
the returned result matched the example, NOT IMPLEMENTED names a method that
still raises NotImplementedError, and FAIL states the differing behavior or
value.
