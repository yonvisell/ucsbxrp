# UCSB XRP software red-team review

Reviewed 2026-08-21 against the current course release, virtual target,
physical-target protocol, IDE, Monitor, commissioning wizard, offline shell,
and folder persistence.
The objective is ordinary laboratory robustness and a low-friction student
workflow, not a safety or security certification.

| Failure mode | Current behavior and evidence | Remaining boundary |
| --- | --- | --- |
| A remembered directory contains unrelated Python files | Commissioning remembers only the parent workspace and never imports its contents. A project directory is loaded only through Open project or a remembered handle with UCSBXRP metadata. The default Expanding spiral project therefore remains intact. Unit and Stable Chrome workflows pass. | A user can still intentionally open a non-course source folder; this is ordinary editor behavior and is never automatic. |
| A fresh Monitor has no project retained by the IDE | The virtual Monitor prepares, validates, and runs the shared Expanding spiral default itself. Physical Run still requires a verified project on the controller. The direct fresh-profile Chrome workflow passes. | None found in the virtual workflow. |
| Run is selected before Validate, or a later run clears earlier output | Run validates first and reports compiler failures in Details without starting. Program output has its own tab; validation, completion, and exception history persist across later runs and reset within the bounded console history. Browser workflows pass. | Reloading the entire application starts a new visible session; project-folder per-run logs remain available. |
| A changed IDE project is run from the Monitor | One content revision is shared across apps; an edit marks it stale and disables Monitor Run until the IDE synchronizes or runs it. Multi-tab Stable Chrome tests pass. | None found in the local workflow. |
| A virtual program never yields, or its owning tab closes | The disposable MicroPython worker has an external owner lease. Owner loss terminates the worker and returns both drive commands to zero; the browser workflow passes. | Browser or OS process death is outside in-page reporting, but reopening creates a fresh target. |
| A live value is malformed, out of range, off-step, duplicated, excessive, or stale | Python declarations, JSON parsing, encoded transport, and the physical endpoint validate independently. State is limited to 16 parameters, 16 watches, 32 KiB, and signed 32-bit slots. Invalid updates preserve the applied value. Unit, service, MicroPython, and Chrome tests pass. | Direct mutation of private Python module state is unsupported student behavior and degrades to an empty browser state. |
| Several watch values overload a sample loop | Watches are staged and serialized once per measured boundary rather than once per call. The service core reads one immutable string and does not build student state during polling. Physical discovery and parameter queuing pass on the attached RP2350. | Quantify worst-case execution cost with 16 rapidly changing watches during later moving calibration; normal course examples stay well below that limit. |
| A slider is moved quickly or a run ends during its debounce interval | Each value is snapped and validated; pending timers are cancelled whenever the target leaves `running`. The latest queued value is applied at the next boundary. | Two independent Monitor tabs are last-value-wins by design; this is visible in the shared pending/applied state. |
| Browser assets come from mixed releases, or a long-open tab stays stale | Assets are content-addressed, the precache is verified before readiness, the preceding cache is retained during transition, and online startup explicitly checks the service-worker script. The prior production tab advanced to the new build during direct Chrome review; the complete shell also ran with networking disabled. | A tab already executing old JavaScript needs its single automatic reload, which is visible as an ordinary page refresh. |
| Cross-origin isolation is missing | Preview and cached responses carry COOP, COEP, and CORP headers. Production headers were read back, and live `SharedArrayBuffer` controls ran in Stable Chrome and the user Chrome session. A non-isolated run reports a direct reload requirement. | Third-party deployment must preserve these headers or use the generated service worker. |
| A folder write is interrupted or permission is lost | Browser backup is independent of the project folder. Workspace and active-project handles are distinct; writes are serialized; Chrome's writable closes each file transaction; four complete pre-overwrite project snapshots rotate before source changes. A remembered project handle that loses permission becomes one explicit Reconnect action. Rotation and real-browser automatic-save tests pass. | A power loss between different files can leave a mixed folder generation; the immediately preceding complete JSON copy is the recovery source. |
| Telemetry or output grows without bound | Plot history, console history, service logs, and recording are bounded. CSV blanks preserve unavailable values; per-run output, metadata, and telemetry rotate as one four-generation bundle. | Long experiments retain the most recent bounded window rather than an unbounded archive. |
| Plot or video export freezes a run, uploads data, or grows without bound | Plot figures are generated from the bounded plot history; world replay uses a stopped recording and an isolated canvas rather than mutating the live world. WebM output is browser-native, remains local, waits for the recorder's actual start event before advancing frames, uses the latest monotonic pose segment after reset, and is capped at 20 seconds of encoded playback. SVG, PNG, and five repeated actual Stable Chrome WebM downloads pass. | WebM requires a Chromium browser encoder and a recording with published pose; the disabled action leaves CSV and plot export available when either condition is absent. |
| Notes obscure plots or accumulate indefinitely | Notes are capped at 24, carry an exact telemetry time and captured pose, and have one global show/hide control. Plot SVG/PNG and world WebM honor the same visible set; run metadata retains the note records. | Notes mark the current time rather than providing a post-run free-form timeline editor; this keeps the control compact and the association unambiguous. |
| Physical transfer is interrupted, a command is retried, or the controller reboots | Projects use alternating slots and an active pointer; commands have correlated cached replies; boot IDs reset log cursors; stop/reset reconnect automatically. The deferred core-1 launch and hardware watchdog close the observed second-run hang. Release dev.4 also feeds an already-active RP2350 watchdog throughout USB writes/readback and from the first boot lines through Wi-Fi association. A full 22-file repair, strict probe, repeated launch, live update, and reset/reconnect pass on the attached controller. | A power loss during transfer can leave the inactive slot incomplete, but the active project and final-written service entrypoint remain intact; rerunning the one provision command repairs it. |
| A student leaves internet Wi-Fi to join the XRP hotspot | The commissioning action waits until the production shell has verified all 183 payloads, including the exact firmware and installer files, before resetting or asking for the network change. The hotspot endpoint is fixed, and the selected station endpoint remains stored when modes change. Network-blocked reload and mode-retention workflows pass in Stable Chrome. | Clearing browser storage requires loading the release again before leaving internet Wi-Fi. The operating-system Wi-Fi selection cannot be automated by the page. |
| The configured station network is absent or changed | A failed association disables station mode and starts the device-specific XRP hotspot at `192.168.4.1`; its status reports the requested mode, effective mode, and station failure without exposing credentials. | The computer cannot discover or join the fallback SSID automatically; the printed device-specific name and fixed course password are the recovery path until USB reprovisioning. |
| An HTTPS public release contacts the XRP's HTTP service | The document primes Chrome's Local Network Access permission before starting the shared physical worker, device requests identify the local target address space, and the service supplies CORS plus legacy private-network preflight headers. Unit tests cover request construction. | Permission is origin-specific. The final GitHub Pages URL still needs its one-time grant against a robot hotspot; non-Chromium browsers are not claimed as course targets. |
| A new or damaged robot has the wrong runtime, partial course files, or an active watchdog | The wizard checks the exact RP2350 and MicroPython release, keeps the watchdog fed, compares all 23 release file hashes, writes changed payloads under temporary names, verifies them, activates each with one direct rename, re-hashes every destination, import-checks XRPLib/course/service modules, and resets only after verification. The attached dev.7 XRP passed a no-change repeat, two deliberate one-file repairs, direct-rename replacement, final imports, and reset; the full state machine and firmware branch also pass in Stable Chrome. | The public-origin native folder-picker-to-Web-Serial sequence and one real Local Network Access grant remain. Bootloader-volume recovery was correctly skipped because this robot already had the pinned firmware; a power loss is recovered by repeating the same action. |
| A repair leaks or overwrites a working network credential | Existing profiles are read back without passwords and retained by default. A newly typed station password exists only in component state until its USB write, is then cleared, and never appears in status or browser storage. New robots default to the credential-free course hotspot workflow. | Browser extensions, operating-system compromise, and a user deliberately inspecting their own live page are outside this local course tool's threat model. |
| Course code and implementation become coupled to one reference algorithm | Tests constrain public records, units, required component behavior, geometry, termination, and path properties rather than private structure or a single tie break. Retained reference source remains revisable build input. | Physical floor calibration should change robot configuration and comparison envelopes, not public component ownership. |
| Compact UI hides state or becomes unusable at smaller widths | Controls use semantic labels and hover/focus help; splitters are pointer- and keyboard-operable; status is text rather than button styling. Wide, narrow, contrast, overflow, and direct Chrome visual reviews pass. | Very small phone layouts are supported for inspection but are not the primary programming surface. |

No unresolved software failure found in this review prevents virtual course
work, project editing, monitoring, offline use, physical connection, or live
parameter tuning. The remaining evidence gaps are the native public-wizard
permission handoff, floor-dependent calibration, worst-case moving telemetry
load, the final Pages-origin network grant, and complete physical challenge
runs.
